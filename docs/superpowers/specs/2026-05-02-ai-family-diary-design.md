## 1. 背景与问题定义

许多家庭存在代际沟通困境：

- **长辈不了解小辈现状**，又因关心而心急，常常好心办坏事或导致关系僵化
- **信息不同步**使家庭对话缺少共同话题，每次聊天都只能重复"吃了吗"，老人想了解近况只能等小辈主动打电话
- **老人不擅长智能产品**，日常也很少被小辈看见和关心

本项目面向**家庭双边用户**（小辈与长辈），通过自动采集小辈日常、AI 合成家书、语音化交付给长辈，让代际沟通恢复"知道对方过得怎样"的基础。

## 2. 目标用户与核心体验

### 2.1 角色与关系

- **小辈（junior）**：佩戴 Insta360 的一方，内容的"生产者"，使用 Web 端审核/发布日记、查看长辈留言
- **长辈（senior）**：内容的"接收者"，使用 Web 端（语音为主、视觉兜底）听日记、提问、留言
- 双方同属一个 `family`，一对一关系

### 2.2 核心体验："AI 日记"

形态为 **A（每日自动日记）**：Agent 每天汇总小辈的 Insta360 素材与社媒动态，生成一篇 200 字左右的第三人称叙事性日记，配 3–5 张精选图。

**小辈端交付节奏：**
- 每日定时生成（默认晚 10 点）
- 弹出通知："今日日记已生成，3 分钟内可编辑/删段"
- 小辈不操作默认自动发布
- 3 分钟倒计时机制平衡"不打扰"与"可控"

**长辈端交付体验：**
- 大字 + 精选图的日记页
- 云 TTS 朗读（温柔女声）
- 底部大红按钮 "🎙️ 按住说话"：按住即暂停 TTS + 录音
- 意图识别：说的是"提问"就走 Q&A + TTS 回答；是"留言"就写入评论
- 视觉兜底：全程按钮可见可点，不强制语音

## 3. 系统架构

五层流水线：

```
① 数据源          ② 摄取&存储        ③ Agent 日记      ④ 双端 Web
─────────────     ─────────────      ─────────────    ─────────────
Insta360 相机  →  FFmpeg 抽帧     →  拉取已可见素材  →  小辈端 (审核/发布)
(真接·预拍)       视觉模型描述        LLM 合成日记       3 分钟倒计时
                  SQLite 素材库       挑 3-5 张图        段落级删除
                  visibility 标签     输出草稿
Mock 社媒 JSON →                                   →  长辈端 (语音化阅读)
(保留接口)                                            云 TTS 朗读
                                                      浏览器 ASR 输入
                                                      意图判定 + Q&A
```

**颜色语义：**
- 绿色（真做）：Insta360 接入、摄取存储、Agent 日记、两端 Web 所有功能
- 黄色（Mock）：社媒数据（用预写 JSON 喂给 ingest 接口）
- 灰色（不做）：OAuth、真推送服务、多家庭、移动端 App、唤醒词、真打断

## 4. 两端核心屏幕

### 4.1 长辈端（阅读 + 语音）

核心布局（自上而下）：

1. 日期行（小字）
2. 日记标题（28px 特大）
3. 封面图（轮播 1/4）
4. 日记正文（22px，大字距）
5. 朗读进度条（"正在朗读 · 第 2/5 段"）
6. 辅助按钮：⏸ 暂停 · ⏭ 下一段
7. **底部主按钮：🎙️ 按住说话**（红色、带阴影，视觉焦点）
8. 按钮副标题："问问题 · 或留言给小明"

### 4.2 小辈端（审核 + 编辑）

核心布局（自上而下）：

1. 倒计时条："2 分 47 秒后自动发送给妈妈"（黄底警示但不压迫）
2. 标题"今日日记草稿"
3. 段落卡片（每段一卡，卡底挂"编辑/删除此段"按钮）
4. 被删除段落保留视觉（划线 + "❌ 已隐藏不给妈妈看"标签）— **给评委展示隐私可控**
5. 封面图横向选择（4 格，可点"+"加图）
6. 底部双按钮：♻ 重新生成 | ✅ 立即发送
7. 页底挂"妈妈的上次留言"卡片

## 5. 数据模型

SQLite，6 张表：

```sql
users (
  id, role ENUM('senior','junior'), name, family_id
)

family (
  id, junior_user_id, senior_user_id
)

raw_clips (
  id, source ENUM('camera','social'), file_path, captured_at,
  auto_caption TEXT,             -- 视觉模型生成的描述
  visibility ENUM('visible','hidden') DEFAULT 'visible',
  created_at
)

diaries (
  id, family_id, date, status ENUM('draft','published'),
  title, body_json,              -- [{id, text, source_clip_ids}]
  cover_images_json,             -- 图片 URL 数组
  published_at
)

comments (
  id, diary_id, author_id, content TEXT,
  audio_url TEXT NULL,           -- 长辈语音留言的原音频
  created_at
)

qa_logs (
  id, diary_id, question TEXT, answer TEXT, created_at
)
```

## 6. API 设计

系统共 10 个端点，围绕"素材流 → 日记流 → 交互流"三条主线组织。本节逐个解释**用途、调用时机、设计考量**，而不仅是签名。

### 6.1 API 一览

| # | Method | Path | 用途一句话 | 调用方 |
|---|--------|------|----------|--------|
| 1 | POST | `/ingest/clip` | 上传一段视频素材，入库并打好描述标签 | 硬件队员的上传脚本 / Insta360 SDK 回调 |
| 2 | POST | `/ingest/social` | 写入一条 mock 社媒动态作为素材源 | 小辈端初始化 / mock 灌入脚本 |
| 3 | GET | `/clips?date=` | 看当天已采集的素材（不含隐藏的） | 小辈端"今日素材"预览页（可选） |
| 4 | POST | `/diary/generate` | 触发 Agent 合成今日日记 | 定时任务（真实使用）/ 演示员（Demo） |
| 5 | GET | `/diary/today?role=` | 拉当天日记；按角色区分"草稿/已发布" | 小辈端审核页 + 长辈端阅读页 |
| 6 | PATCH | `/diary/:id` | 小辈改标题、隐藏某段 | 小辈端审核页 |
| 7 | POST | `/diary/:id/publish` | 将草稿翻牌到已发布 | 小辈端点"立即发送" / 倒计时到期自动 |

| 9 | POST | `/diary/:id/comment` | 文本/语音留言写入评论区 | 小辈端评论框 / 长辈端备选打字入口 |
| 10 | POST | `/diary/:id/ask` | 长辈的一句语音文本 → 意图分流 → 答或留言 | 长辈端"按住说话"松手时 |

### 6.2 素材流（1–3）

**设计原则：** 所有"外部数据进入系统"的入口都统一为 `raw_clips` 表。相机视频和社媒动态结构本不同，但都被归一化为"一条带时间戳和文字描述的素材"，这样下游 Agent 只需要面对一种数据形态。

#### ① POST `/ingest/clip`

- **用途**：硬件队员把 Insta360 的视频片段上传到服务器后，调用这个接口把素材入库。服务端根据 `file_path` 去调 FFmpeg 抽关键帧、调视觉模型生成自然语言描述，最终写入 `raw_clips` 表，默认 `visibility='visible'`。
- **调用时机**：
  - **真实使用**：硬件端 SDK 在剪出一个"场景段"后调用（可能几分钟一次）
  - **Demo**：演示开始前，硬件队员把当天拍的所有素材预先通过这个接口全部上传（避免现场跑 pipeline 翻车）
- **设计考量**：
  - **`auto_caption` 允许前端直传**：有些场景（如社媒帖子）前端已经有文本描述，不需要再走视觉模型。API 允许跳过描述生成，直接存。这让 `/ingest/clip` 既能被硬件用（带视频文件 + 无 caption → 触发视觉模型），也能被 mock 脚本用（直接带 caption → 跳过生成）。
  - **`visibility` 默认 visible**：符合"大多数素材默认给看"的心智。隐私敏感素材由小辈主动标 hidden（通过未来的 admin 操作或 `PATCH /clips/:id` — 本期不做）。
  - **不做去重**：两次上传同一 `file_path` 会产生两条记录。24h 内不值得做去重，实际使用也不会出现重复上传。

#### ② POST `/ingest/social`

- **用途**：把一条社媒动态（mock JSON）写入 `raw_clips`，`source='social'`。内容（`content`）直接落到 `auto_caption` 字段——社媒帖已经是文本，不需要视觉模型。
- **调用时机**：
  - **真实使用**：后台任务拉 OAuth 授权后的社媒 API（本期不做）
  - **Demo**：演示前一次性灌入一批 mock JSON（5–8 条，和相机素材共同构成"今天发生的事"）
- **设计考量**：
  - **保留独立端点而非合并进 `/ingest/clip`**：虽然它们最终都写 `raw_clips`，但社媒没有 `file_path`（有 `image_urls`），结构不同。分开端点让两边 schema 各自清晰，也方便未来独立加限流/鉴权。
  - **`image_urls` 取第一张作为 `file_path`**：为了统一下游 Agent 的"每条素材至少有一个视觉抓手"的假设。如果没图，`file_path` 留空，Agent 就把它当纯文字素材。

#### ③ GET `/clips?date=`

- **用途**：查当天已采集并**对 Agent 可见**（`visibility='visible'`）的素材。返回按时间排序的列表。
- **调用时机**：
  - 小辈端想让用户看"今天都采集到了什么"的预览页（非必要，但有助于用户理解 Agent 生成的日记来源）
  - 调试/demo 讲解时展示"数据流起点"
- **设计考量**：
  - **隐藏素材不返回**：`visibility='hidden'` 的素材从这个端点就看不到，保持"隐藏就是隐藏"的一致性。如果未来要做"草稿箱"式的素材恢复功能，再加 `?include_hidden=true` 参数。
  - **按日查询而非分页**：日记本身就是"按日"组织的产品，API 顺应这个心智。

### 6.3 日记流（4–8）

**设计原则：** 日记的生命周期是 **generate → (edit) → publish → archive（history）**。每个状态用 `diaries.status` + `published_at` 两个字段表达，避免为每个状态建一张表。

#### ④ POST `/diary/generate`

- **用途**：核心 Agent 触发点。服务端拉当天所有 `visible` 的 `raw_clips`，把它们的 `auto_caption` 喂给 LLM，LLM 返回结构化 JSON（标题 + 段落数组 + 代表图 clip_id 列表），入库为一条 `status='draft'` 的日记。
- **调用时机**：
  - **真实使用**：每日 22:00 定时任务（可用 cron/APScheduler；本期放在前端定时器/手动触发）
  - **Demo**：演示员在"数据已入库"后手动调用，现场生成日记
- **设计考量**：
  - **只看 `visible` 素材**：这是隐私机制的第一道闸——标为 hidden 的素材 LLM 根本看不到，从源头切断"AI 不小心把不该说的说出来"的风险。
  - **返回整份草稿而非 diary_id**：小辈端调用后通常紧接着要展示草稿，一次返回省掉第二次 GET。
  - **允许重复生成**：同一天多次调用会生成多条 draft 记录（`GET /diary/today?role=junior` 返最新一条）。这样小辈觉得"这篇不好"可以直接重跑，不用先删旧的——降低心智负担。真实使用里 23:59 前的最后一条生效。
  - **body_json 是段落数组**：每段带 `source_clip_ids`，既方便小辈定位"这段从哪来"，也为未来"点段落看原素材"的交互预留。每段还有 `hidden` 布尔——事后删段不真删数据，只标隐藏，这样 PATCH 能撤销、QA 能定位。

#### ⑤ GET `/diary/today?role=`

- **用途**：拉"今天"的日记。通过 `role` 参数实现**同一 URL 服务两类用户**：
  - `role=junior`：返回最新一条日记，无论 draft/published，**返回所有段落**（包括 hidden 的，让小辈看到自己之前隐藏的东西）
  - `role=senior`：返回最新 `published` 的日记，**过滤掉所有 `hidden=true` 的段落**；如果当天没有 published，返 404（长辈看到"今日无日记"的空状态）
- **调用时机**：
  - 小辈端打开 app 时加载审核页
  - 长辈端打开 app 时加载阅读页
  - 长辈端 TTS 播放完毕想"重新听"时重新拉
- **设计考量**：
  - **`role` 参数而非两个独立端点**：数据源本质相同，只是过滤规则不同。用参数控制能共享绝大多数代码路径。
  - **senior 未发布就 404 而非空对象**：明确区分"今天没更新"和"今天有但隐藏了"，前端可以显示专门的空态提示。
  - **不做 ETag/缓存**：24h demo 不值得；数据量极小，每次重查成本可忽略。

#### ⑥ PATCH `/diary/:id`

- **用途**：小辈在审核期内编辑日记——改标题、改段落文字、标段落为 `hidden`。
- **调用时机**：
  - 小辈点"编辑"按钮改文字时（保存时触发）
  - 小辈点某段的"删除"按钮时（把该段 `hidden` 改 true）
  - 小辈改标题时
- **设计考量**：
  - **PATCH 而非 PUT**：body 里的字段都是可选的（`title` 和 `paragraphs` 各自独立），只传要改的那部分。
  - **发布后拒绝编辑（409）**：一旦 `published`，就不能再改——否则长辈看到的内容会"变身"，破坏信任。要改只能重生成（等同于发新日记）。这里选 409 Conflict 比 403 Forbidden 更语义化（状态冲突，不是权限问题）。
  - **"删段"是打标不是删除**：把段落 `hidden=true` 保留在 `body_json` 里，让小辈能取消隐藏。这个设计也保证 QA 端点（⑩）能看到完整的日记上下文，回答时不会因为"日记里根本没提这段"而无法解释长辈看到的某些线索（虽然长辈看到的是过滤后的版本，但 Q&A 以公开版本为准）。

#### ⑦ POST `/diary/:id/publish`

- **用途**：把 `draft` 翻成 `published`，写 `published_at` 时间戳。翻牌后这份日记对长辈可见。
- **调用时机**：
  - 小辈在 3 分钟倒计时里点了"立即发送"按钮
  - 3 分钟倒计时到期（前端自动调用）
- **设计考量**：
  - **独立端点而非 `PATCH /diary/:id {status: "published"}`**：发布是一个"事件"不是一个"字段变更"——它还要打时间戳、未来可能要触发通知。把它单独开一个端点，语义清楚、便于未来加副作用（比如 webhook 通知长辈端）。
  - **已发布再调返 409**：保证"发布"是不可逆的单次动作，避免前端抖动导致 `published_at` 被刷新。
  - **不做"撤回"**：真实使用里撤回的需求很低（而且撤回后长辈可能已经看到了），24h 也做不完。

#### ⑧ GET `/diary/history`

- **用途**：拉最近 N 篇已发布的日记，按 `published_at` 倒序。长辈端"时光机"翻阅用。
- **调用时机**：
  - 长辈端滑到底部想看昨天/前天
  - （未来）导出/分享某一天时
- **设计考量**：
  - **只返 published**：草稿不是"历史"，是"未完成"，不能混进来。
  - **默认 limit=20**：够长辈翻小两周。上限 100，防止前端乱传 `limit=99999` 把后端拖死。
  - **不按 family 过滤**：本期只有一个 family，后期加多家庭时再加 `family_id` 过滤或从 auth 推断。

### 6.4 交互流（9–10）

**设计原则：** 长辈的每一次语音输入可能是"问我儿子今天怎么了"也可能是"告诉我儿子我想他了"——同一个入口，由意图判定器分流。我们没有给长辈端设两个按钮（"提问"/"留言"）因为这对老人是认知负担，也违反"按住说话，自然交流"的产品主张。

#### ⑨ POST `/diary/:id/comment`

- **用途**：写评论。文本必填；语音留言的场景还可以带 `audio_url`（指向已上传的音频文件，供回放）。
- **调用时机**：
  - 小辈在"妈妈的留言"下点回复
  - 长辈在嘈杂环境下选择打字备选入口
  - 由 `/ask` 端点的"comment"分支内部调用（不走 HTTP 调用自己，而是直接写同一张表）
- **设计考量**：
  - **`audio_url` 可选**：语音留言保留原音频让对方能听到妈妈的声音（比纯文字温度高），但 ASR 转写的文字也存，方便小辈快速 scan。
  - **`author_id` 由前端传**：本期无鉴权，前端在 session 里维护当前角色的 user_id。真实产品里会从 auth 推断。
  - **挂在 diary 下而非独立 `/comments`**：评论的语义就是"针对某篇日记的反馈"，URL 体现这个父子关系，RESTful 且易读。

#### ⑩ POST `/diary/:id/ask`

- **用途**：长辈端"按住说话"松手后的入口。前端已通过浏览器 ASR 转成文字，把文字提交到这里。服务端做三件事：
  1. 调意图判定器分出 `question` 或 `comment`
  2. 如果是 question：取日记 published 版本（过滤 hidden 段）喂给 QA LLM，返回答案文本，写 `qa_logs`
  3. 如果是 comment：把文字写入 `comments`（内部直接 insert，不绕 HTTP）
- **返回**：`{intent, answer?, comment_id?}`。前端根据 `intent` 分支渲染：
  - `question` → 拿 `answer` 调 TTS 播报
  - `comment` → 显示"已发送给小明"的确认
- **调用时机**：长辈端的核心交互端点，demo 的"高潮"就靠它。
- **设计考量**：
  - **合并端点而非两个端点**：前端不知道用户说的是问题还是留言（事实上长辈自己也不是总能分清），**分流由服务端的 LLM 做**。这是产品哲学：认知成本留给后端。
  - **意图判定即使错了也不会崩**：判定成 question 时，LLM 实在答不出会回"日记里没有说这个"，长辈听到这个反馈也不突兀；判定成 comment 时，即使是个问题被当成留言发给了小辈，小辈看到后自己会意会。错分成本很低。
  - **`qa_logs` 和 `comments` 分表而非合表**：它们语义完全不同——qa_log 是"和 AI 的问答"（私密、不发给小辈），comment 是"家人之间的留言"（对方必须看到）。分表防止 demo 里长辈问"他今天吃什么"被错误推送给小辈。
  - **不把 QA 历史返给前端**：每次 `/ask` 只返当次答案。历史问答未来可以用 `GET /diary/:id/qa-history` 单独查（本期不做）。

### 6.5 整体调用链路（Demo 情境）

以 Demo 故事线为例，10 个 API 的真实调用顺序：

```
[Demo 前准备]
  硬件队员 × N:   POST /ingest/clip    （每段视频一次）
  mock 脚本 × 5:  POST /ingest/social  （灌入今日社媒）

[Demo 0:30-1:00 数据展示]
  演示员:         GET  /clips?date=2026-05-02   （后台看素材列表）

[Demo 1:00-2:00 小辈端]
  演示员:         POST /diary/generate          （Agent 生成日记）
  小辈端:         GET  /diary/today?role=junior （拿到草稿）
  小辈端:         PATCH /diary/:id              （删段，标 hidden）
  小辈端:         POST /diary/:id/publish       （翻到已发布）

[Demo 2:00-3:30 长辈端高潮]
  长辈端:         GET  /diary/today?role=senior （拿已发布的版本，hidden 已过滤）
  长辈端 (问):    POST /diary/:id/ask           （intent=question, 拿 answer → TTS 播报）
  长辈端 (留言):  POST /diary/:id/ask           （intent=comment, 写入 comments）

[Demo 3:30-4:00 情感闭环]
  小辈端:         GET  /diary/:id/comments      （本期合并在 /diary/today 的响应里，或新加端点；MVP 省略）
```

（注：显示妈妈留言在 MVP 里可以走最简单的路径——小辈端定时轮询 `/diary/today?role=junior`，响应扩展带上 `comments` 数组；不必新加独立端点。这属于渲染层细节，留给前端团队决定。）

| Method | Path | 用途 |

## 7. 筛选机制（隐私控制）

**两个时机 + 一个默认规则：**

1. **事前**（素材入库时）：`raw_clips.visibility` 默认 `visible`，可手动改 `hidden`。`hidden` 的 clip 在 `generate` 时 LLM 根本看不到，实现"根源性保护"。
2. **事后**（日记发布前 3 分钟）：小辈在 `body_json` 中对某段点"删除"，这段不会写进 `published` 版本。
3. **默认**：visible + 3 分钟倒计时自动发布，平衡负担与可控。

Demo 时展示"事后删段"（视觉冲击强），口播补一句"更彻底的做法是事前标隐藏"。

## 8. 技术栈

**架构形态：前后端分离**（前端独立 SPA，后端纯 API 服务，通过 HTTP/JSON 通信）

| 模块 | 选型 | 备注 |
|------|------|------|
| 前端 | React + Vite + Tailwind | SPA，两端共享组件 |
| 后端 | **Python + FastAPI** | 单进程，异步支持好，与 LLM/FFmpeg 生态契合 |
| 数据库 | SQLite（本地文件） | 零部署；用 SQLAlchemy 或直连 |
| 视频抽帧 | FFmpeg（subprocess 调用） | 命令行 |
| 视觉理解 | Claude Sonnet 4.6 / GPT-4o | 多模态，用 anthropic 或 openai SDK |
| 日记生成 | Claude Sonnet 4.6 | 中文叙事强；带 prompt caching |
| ASR | 浏览器 `SpeechRecognition` API | Chrome 内置，免费，前端直调 |
| TTS | 火山引擎 或 讯飞 | 前端获取鉴权 token 后直调；或后端代理 |
| 意图判定 | LLM 一行 prompt | 后端 `/diary/:id/voice` 端点内完成 |
| 相机接入 | Insta360 官方 SDK | 硬件队员负责，产物落本地后调 `POST /ingest/clip` |
| 跨域 | FastAPI CORSMiddleware | 允许前端 dev server |
| 部署 | 本地 + 内网 Demo | 前后端分别启动；演示机器装 Python 3.11+ 和 Node 20+ |

## 10. 风险与预案

按杀伤力排序：

### 🔴 高风险

1. **TTS 现场调 API 失败**（网络/鉴权）
   - **决策：** 已明确不做预生成音频 fallback，信任网络
   - **补救：** 至少在代码里留 `try/catch`，失败时前端友好提示而非崩溃
2. **ASR 嘈杂环境失效**
   - **预案：** 长辈端加"太吵？点这里打字留言"备选入口
   - **硬件：** 带一支领夹麦备用

### 🟡 中风险

3. **LLM 日记生成像机翻 / 不温暖**
   - **预案：** Prompt 里加 3 个 few-shot 示例（人肉写的优秀样本）；预备 2-3 个"保底日记"
4. **Insta360 上传链路不稳**
   - **预案：** 硬件队员 demo 前完成全流程，素材已传、日记已生成；现场演示是"重跑"或直接展示

### 🟢 低风险

5. **麦克风权限弹窗**
   - **预案：** demo 前预授权 Chrome 对 localhost 的麦克风
6. **时间不够**
   - **砍掉优先级**（从先砍到后砍）：
     1. 评论系统
     2. 小辈端"重新生成"
     3. 段落级删除（退回整篇删/留）
     4. 历史日记翻阅

## 11. 明确砍掉的功能（YAGNI）

| 功能 | 原因 |
|------|------|
| 用户注册 / 多家庭 | Demo 单家庭足够 |
| 真社媒 OAuth | Mock JSON 同效 |
| 移动端 App | Web 能演，App 拉长周期 |
| 通知推送服务 | 轮询 + 小红点够用 |
| 唤醒词监听 | 按钮单按替代 |
| 真"边播边打断" | "按住说话→暂停 TTS"体验基本一致 |
| 视频剪辑 / 高光集锦 | A 路线不需要 |
| 用户画像 / 数据分析 | 黑客松不需要 |
